# autonima: design direction

## 1. Diagnosis — what is actually wrong

The measured evidence says the LLM stages work. Precision rises at every screening stage in **8 of 8 projects** (PAPER_OUTLINE.md §1); screening retention is 0.93–0.97; executive_function's annotation F1 is 0.87 at v1 and 0.95 at v2. In every documented failure, **the model applied the specification faithfully and the specification was wrong** (`projects/executive_function/v2.yaml:39`). There is no evidence anywhere in this corpus that a better model would move a headline number.

So the product's problem is not capability. Look at what the failures actually have in common:

| failure | what the pipeline knew | what it reported |
|---|---|---|
| problem_solving v1 dead retrieval root | `Path(root).rglob('*')` → `[]`, then `FileNotFoundError` swallowed at `pipeline.py:666` | run completed, exit 0, F1 0.249 |
| decision_making v2/v3 mangled YAML key | `exclusion_criteria/home/zorro/.../v1.yaml:` carrying 2 real exclusions | `criteria_mapping.json`: `GLOBAL_E: 0`. Verified: **zero** GLOBAL_E ids in v3's mapping |
| executive_function v1 abstract screening | model cited criterion ids in prose | **3337 of 3538 exclusions (94.3%)** have an empty `exclusion_criteria_applied` |
| social v2 abstract screening | same | **313 of 314 (99.7%)** empty |
| dementia v3 NiMADS export | 146 of 478 analyses never evaluated for a column | exported as `False` — byte-identical to "evaluated and rejected" |
| dementia v2 quota exhaustion | 1,558 × HTTP 429 + 30 × invalid-model | written to `<run>/abstract_screening_results.json` **outside `outputs/`**, where nothing reads it |
| vbm_of_ptsd `increased_gm` | one of five distinct skip paths in `meta.py` | an empty directory, in all three runs of that project |
| social `v3-all_pmids` vs `-multi_analysis` | all seven stage hashes identical, configs differ by one line (output dir) | two differently-named runs, planned in PAPER_OUTLINE.md:651 as a prompt-type contrast |

That is not eight problems. It is one problem with eight faces: **autonima is a measurement instrument that does not record its own operating conditions.** Every number it emits is a point estimate with no denominator, no provenance and no error bar, and it has no way to distinguish "this measured zero" from "this measured nothing."

Two consequences follow, and they set the leverage.

**(a) The specification has no feedback loop, and humans have been closing it by hand.** A user writes prose; the prose becomes tens of thousands of decisions; the only channel back is a gold standard they do not have. Every successful spec repair in this corpus — executive_function v1→v2, social v3→v4, dementia v4→v5 — was a human manually reconstructing criterion-level attribution *from data the pipeline already wrote and then discarded*, and in social's case by regex-scraping generated HTML. The reason "specification is the hard part" is not that specs are hard to write. It is that writing one is an open-loop control problem. Reconnecting that loop is the highest-leverage thing the product can do, and the wire is already in the building: the model states which criterion it applied on every decision.

**(b) Retrieval is a genuine capability gap wearing a legibility gap on top.** The 49% coordinate yield (§8c) is real and larger than every schema effect in the paper combined. But the *product* cannot currently tell a user where in the funnel a paper died — in dementia v3, 994 of 1001 `missing_fulltexts.csv` rows say `type=unavailable, source=pubget` with an empty path, undifferentiated, even though the split (762 no-PMCID, 239 PMCID-but-no-text) is reconstructible from `study.pmcid` already on disk. You cannot prioritise acquisition effort against a number you cannot decompose. Ship the legibility first; it is a day, and it is the precondition for spending money on the capability half.

**The claim.** autonima's leverage is not in its models. It is in making a run *legible* — to the user during authoring, to the author during revision, and to a reviewer afterwards. Nearly every accepted item below is post-processing of data the pipeline already produces and throws away. That is why this roadmap is cheap relative to its impact, and it is why "add a better model" appears nowhere in it.

## 2. Themes

### A. Refuse to emit a number that measures nothing
**TLDR: add pre-flight checks, and abort on fatal config errors instead of running anyway.**
*Changes for the user: a misconfigured run fails in seconds instead of publishing a metric measured against a dead path.*

### B. Close the specification feedback loop
*Changes for the user: "which of my criteria is doing this, and to whom" becomes a query instead of an afternoon.*

### C. Establish the noise floor before believing an effect
*Changes for the user: they can tell a spec improvement from a coin flip.*

### D. See the search ceiling before paying for it
*Changes for the user: the unrecoverable loss is visible in seconds of esearch, not after a full run.*

### E. Make the extraction funnel visible and the missing papers actionable
*Changes for the user: the dominant bottleneck becomes a ranked worklist instead of an undifferentiated 994-row CSV.*

### F. Make an expensive run cheap to own
*Changes for the user: a crash at study 380 of 400 costs minutes, and the run has a price.*

## 3. Theme A — Refuse to emit a number that measures nothing

**TLDR.** Before a run starts, resolve and count everything the config declares — every
full-text source root, every key, every path. If something is fatally wrong, **abort**; do not
run and report a number anyway. Two rules cover most of it:

1. **A declared source that does not exist is a fatal error, not a warning.** `problem_solving`
   pointed two of its three full-text roots at a path from another machine, silently retrieved
   nothing from them, and published a screening F1 of 0.249 that measures a dead path rather
   than the criteria.
2. **An unrecognised config key is a fatal error, not something to ignore.** `decision_making`
   carried a file path glued onto a YAML key; pydantic dropped it, and three completed runs plus
   one live one annotated with zero global exclusions.

The point is *abort*, not *log louder*. `problem_solving` did log an error — `pipeline.py` calls
`log_error_with_debug`, which is `logger.error` and nothing else — then exited 0 with a
complete-looking output. A warning in a run that takes hours is a warning nobody reads.

This is deliberately narrow. It covers only things knowable before any work happens: a directory
that isn't there, a key that isn't real, a source that yields zero. Papers that are individually
unreachable (paywalled, no PMC deposit) must keep being skipped and recorded, not fail the run —
that is normal, and making it visible and actionable is Theme E, not this.

**Convergence: this theme is the single strongest signal in the whole review.** Preflighting full-text sources was independently proposed by *three* lenses (spec-authoring R2, retrieval-extraction #1, reproducibility #1) and named as the strengthened first item of a fourth (validation-without-gold's tracer proposal). All three drew the same conclusion from the same defect. Treat that as settled.

**A1. Retrieval preflight + loud zero-yield.** Three sub-parts, in strict order of value:

1. **Split the `try:`.** `pipeline.py:581` wraps the *entire* `for full_text_config in full_text_sources` loop, with the handler at `:664` calling `log_error_with_debug` (which is `logger.error` and nothing else, `utils/base.py:26`) and never appending to `self.results.errors`. So one bad source aborts every later source *and* the summary's "Errors encountered" block (`cli.py:172-176`) stays empty. ~5 lines. Do this first — it converts a silent zero into a visible failure for both the raising (`iterdir`) and non-raising (`rglob`) source shapes.
2. **Existence check.** A declared `root_path` that does not exist or is not a directory always raises — no `allow_empty` escape, because no value of that flag expresses "I meant to point at a directory that isn't there." Skip paths containing `<...>` placeholders so `template_/v1.yaml` doesn't trip. A root that exists but yields zero PMID-shaped entries is a *warning* at validate time (scope is unknown before search) and a structured error at run time.
3. **Fix the two dead checks.** `config.py:284` does `hasattr(source, 'coordinates_path_templates')` on a plain dict (`full_text_sources: List[Dict[str, Any]]`) — always False; the mutual-exclusivity rule has never once fired. The retrieval loader's `if hasattr(retrieval_config, key)` silently drops typos.

**A2. Three configs, at least one shipped run, every global annotation exclusion silently dropped. `screening_config.abstract.update(...)` accepts any key at all; `load_from_dict` uses `.get()` throughout so unknown top-level keys vanish too. Also silently discarded: `annotation.include_all_analyses` (social v2), `annotation.local_evidence` (social v1-annotation-only-lc). ERROR level for screening/retrieval/annotation/top-level, with `--allow-unknown-keys` for the `baselines.yaml` files that legitimately carry `meta_pmid`/`shared`.

**A3. Declare the extraction toolchain.** `setup.py` has no `ace` extra and CLAUDE.md's documented install is `pip install -e .[llm,meta,readability,ui]`; `find_spec('ace')` is None in this environment. `_load_ace_api()` raises `ACEProcessingError`, which the fallback candidate gate calls for every table not matched in `coordinates.csv` (~762 of 864 in dementia v3), and it lands in a bare `except Exception` at `utils/utils.py:866` that logs and returns `analyses, {}`. Split by risk: the manifest fingerprint (`ace.__version__`, `GATING_VERSION` — both already gathered by `_ace_source_fingerprint` and thrown away — plus readabilipy/Node, autonima and Python versions), the `ace` extra, and a Toolchain section in `validate` are pure additions, ship now. `parsing.table_gate: strict|candidate|off` ships separately, defaulting to `candidate`. **A4. Failure ledger, backoff, and a circuit breaker.** Success writes to `self.result_dir / "outputs"` (`screener.py:539`); failure writes to `self.result_dir` (`:567`). Six orphaned files exist. dementia v2's holds 1,588 rows — I opened it: 1,558 HTTP 429 quota-exceeded, 30 invalid-model. dementia v1's holds three rows whose `reason` is a genuine Python `TypeError` swallowed by the blanket `except Exception` and persisted as data.

Two contract fixes, ten minutes each.** `--copy-valid-cache-from` appends `"outputs"` internally, so passing `<run>/outputs` copies nothing and logs nothing (the confirmation is gated on `if copied`). ## 4. Theme B — Close the specification feedback loop

**Convergence: three lenses independently landed on criterion-level attribution as a first-class artifact** (spec-authoring #3, error-feedback #2, validation-without-gold #2), each arriving from a different documented failure. Two lenses independently landed on content-hashed criterion ids (spec-authoring #3, error-feedback #4), and three on a spec differ (spec-authoring #5, error-feedback #4, reproducibility #4).

**B1. `inclusion_criteria_not_met` — the substrate. This is the highest-value single build in the document.**

The decision record cannot express *"excluded because inclusion criterion I3 was not met."* Only the met sets are structured. Measured: 94.3% of executive_function v1's abstract exclusions, 99.7% of social v2's, and 71.0% of social v4-annotation-only's custom-annotation exclusions carry no exclusion code at all. The schema is already working around its own missing field — `validate_criteria_ids` does `crit_id.upper() in reasoning_upper`, string-matching its own free-text prose.

The prose fallback was tested and it does not work. `screening/prompts.py:106` and `:222` *already* instruct the model to state "(c) inclusion IDs not met," and `annotation/prompts.py:250` says "explicitly name missing inclusion IDs in reasoning." The fraction of code-less exclusion reasons containing a machine-parseable not-met section is 33% (ef v1), 1% (social v2), **0%** (dementia v1) — same model in all three. Asking harder in prose has been tried and has failed.

Ship the additive field only — `inclusion_criteria_not_met: List[(id, evidence_span)]` on both screening outputs and the dynamic `_DecisionBase`. Defer the `criteria_verdicts` refactor, which touches three schemas, both prompt builders and every consumer for no verified gain. **Require a short verbatim evidence span per not-met id**: in ef v1-annotation-only, `GLOBAL_I1/I3/I4` are each cited exactly 336 times — the model already mechanically enumerates every inclusion id on inclusion, and a `not_met` list will otherwise be filled with the mechanical complement. Delete clause (c) from both screening prompts and the annotation self-check in the same commit. Do **not** bump `CACHE_SCHEMA_VERSION`: `prompt_version` is already folded into `stage_hash`, so the prompt edit invalidates every screening stage anyway; ship the field, the prompt change and a no-LLM back-fill together and make readers absent-tolerant. Before rolling out, run it on 200 executive_function abstracts and check the not-met lists are not simply the set complement of the met lists — if they are, the field is decoration and the rest of Theme B needs re-planning.

Cheap prerequisite worth landing alongside: port annotation's `validate_criteria_ids` requirement into `screening/schema.py`, so an `EXCLUDED` decision with a non-empty `criteria_mapping` must carry a code. Annotation's attribution coverage is 85% precisely because it has that validator; screening's is 52% because it does not.

**B1a. The obvious objection, and why it fails.** The natural response to B1 is that the field is redundant: `inclusion_criteria_applied` is *instructed* to be exhaustive (`screening/prompts.py:99`, "include ALL inclusion criteria IDs that are satisfied"), and inclusion requires every criterion to be met (`:200`, "Verify that ALL inclusion criteria are met"). If both hold, not-met is simply `ALL − met`, and B1 is a reporting change rather than a schema change.

Both premises are stated in the code. The model does not honour the first, and this can be shown without any gold standard by using **included papers as a ground-truth control**: an included paper met all four criteria by definition, so it must list all four.

In `executive_function/v1` abstract screening (4 inclusion criteria, 1,318 included papers):

    ids listed on an INCLUDED paper    papers
      4 (correct)                        745
      3                                  448
      2                                  111
      1                                   10
      0                                    4

**43.5% under-report.** On records whose true not-met set is known to be empty, the complement manufactures **716 false "not met" attributions**, and they are not uniformly distributed:

    I2  healthy participants     417 false accusations
    I4  executive function       238
    I3  fMRI or PET               50
    I1  English peer-reviewed      11

I2 is the criterion at the centre of the executive_function diagnosis — the healthy-adults gate that the benchmark demonstrably does not apply. The complement over-blames precisely the criterion that most needs an honest count, which is the worst possible failure mode for a signal whose entire purpose is deciding which criterion to rewrite.

On excluded papers the complement is *mostly* right. Comparing it against the not-met set the prose explicitly names, where it names one: 2,437 agree and 270 disagree — **90.0% vs 10.0%**. Ninety percent is not nothing, and it is why the objection is reasonable. But a 10% error rate is the wrong thing to accept on the one number used to justify rewriting a criterion, and the errors concentrate in the highest-traffic clauses.

**The distinction the complement structurally cannot represent.** `prompts.py:106` asks for "inclusion IDs **not met or not demonstrated**." Those are different findings:

- *not met* — the abstract states a schizophrenia sample; the healthy-adults criterion is genuinely violated, and the criterion is working
- *not demonstrated* — the abstract simply never mentions the sample, and the criterion is being applied to absent information

The complement collapses both into "not met." That confound is live in the paper: §8a attributes executive_function's abstract-stage false negatives to over-strict user criteria, while 26–30% of stored abstracts corpus-wide are single-section fragments with METHODS and RESULTS discarded before the screener sees them (see §11 item 1). Until *violated* can be separated from *never stated*, specification error and information starvation are not identifiable, and the paper's flagship "the spec was wrong" case rests on the ambiguity.

This is also the argument for requiring a short verbatim evidence span per not-met id rather than a bare list. Without it the model can satisfy the field with the arithmetic complement, and the result is the same 90%-accurate number in a new shape — at full token cost.

**B2. `autonima criteria-profile` — a navigator, not a verdict.**

The gold-free counting already exists, outside the package: `scripts/compare_screening_to_benchmark.py:747 _count_stage_criteria_usage` returns per-criterion citation counts from nothing but the applied arrays. Lift it into `autonima/reporting/criteria_usage.py`, run at the end of each LLM stage, emit `outputs/criteria_usage.json` + CSV, and extend it to annotation (which has no gold-free usage table at all).

One for two.

- Do not auto-run it inside `_generate_basic_outputs` until the framing is settled. A file named `criteria_report.json` will be read as a verdict no matter what the header says. Ship it as `criteria-profile`.

**B3. Criterion-scoped review, not decision-scoped.** This is the corrected form of the adjudication proposals, both of which were judged **weak** in their original shape and for the right reason: self-adjudication measures *spec-application fidelity*, not *spec correctness*. In executive_function the model applied the spec faithfully; an author reviewing "excluded: schizophrenia sample, cites the healthy-adults gate" against their own written criteria would mark AGREE, correctly, while recall against the real target was catastrophic. Worse, the proposed sampler — low-confidence, unstable, boundary cases — routes systematically *away* from those 30 FNs, which were high-confidence, stable and unambiguous.

So invert the unit. Drive review from B2's sole-cause index and ask **"do you endorse this criterion, having now seen the 30 papers it alone rejected?"** — one judgement per criterion instead of 2,357 per run, which is exactly what the executive_function author produced by hand (five spec edits, not 30 per-study labels). Fork `scripts/generate_parser_failure_annotation_report.py`, which already has radio/localStorage/export machinery proven in this workflow, rather than building a webui tab. Emit a proposed spec edit against the stable criterion key. **Do not compute or display any user-grounded precision number at any adjudication count** — with no second rater it is not a quality metric, and labelling it "self-adjudicated" will not stop it appearing in a results table.

Bump a `schema_version` on `criteria_mapping.json` so the results-repo scripts fail loudly rather than misjoin.

Extend it: accept the id, record it in `cross_bucket_citations`, emit one WARNING naming the criterion. ~20 lines, zero false positives, eliminates that whole failure class regardless of YAML wording. Also make `client.py:196` append the pydantic error to the retry prompt instead of resending the identical prompt three times, and persist the failing study's raw response on exhaustion instead of dropping all its annotations. Add a `failed` counter to `AnnotationProcessor.cache_stats` (today `{reused, processed}` only) — the 25-study loss went through `"Continue processing other studies"` with no number anywhere.

**B7. PRISMA excluded-with-reasons.** `abstract_excluded_by_reason` / `fulltext_excluded_by_reason: {criterion_id: count}` in `prisma_stats`, plus `excluded_with_reasons.csv` next to `missing_fulltexts.csv`. ~50 lines on top of B1. It is required by PRISMA 2020, it is what a journal reviewer asks for, and it finally gives `output.prisma_diagram` — a config flag that is hashed into the output stage signature, serialised, and **consumed nowhere** — something to mean.

**B8. Deterministic lint, narrowly scoped.** Two rules only.

- **Shared-phrase duplication (the good one).** "against an active control" appears in `executive_function/v1-annotation-only.yaml` at line 56 (`GLOBAL_E1`) and in seven per-domain criteria at 68/74/82/90/98/106/114. v2's header records that leaving them "would have silently preserved the restriction even with the global one gone." Report as "these N criteria share this phrase; edits must be made together." Near-zero false-positive cost.
- **Polarity, narrowed to `\bEXCLUDE\b|\bmust not\b|disqualif` on inclusion criteria, INFO level only.** The originally-proposed trigger set fires on 45–56 of ~900 inclusion criteria (~5–6%), and the extras are overwhelmingly *permissive* language: "Any participant group qualifies," "Do not require an overt response," "missing one or more of these details alone should not exclude a study." Those two executive_function lines **are the successful repair of the documented failure**. A lint that flags the fix is worse than no lint. Narrowed, it drops to ~2.7% with roughly half genuine.

Drop the contradiction rule entirely: tested against `social/v3-annotation-only`, the isolate-vs-multi-label pair stays **silent on the broken config and fires on the fixed one** (the multi-label policy only appears in v4). Drop the LLM-adjudicates-prose rule — there is no ground truth for it. For the non-predicate/guidance problem, do not add a new `guidance:` key to screening: `screening.<stage>.additional_instructions` already exists and is already injected into both prompts, and `annotations[].description` covers per-annotation. Only **global annotation guidance** is genuinely missing; add that one field, un-ID'd. (It matters: in ef v2-annotation-only, `GLOBAL_I1` — "Scope- You are judging ONE analysis, not the paper" — is cited 327 times, poisoning every downstream count.)

**B9. `autonima preview --repeats k` and `--against` — ship the delta, not the engine.** The engine already exists and the authors already use it: `pmids_file` + `screening.{abstract,fulltext}.skip_stage: true` + local sources is, verbatim, "reuse a prior run's retrieval tree and run one LLM stage on a fixed list," and every project has annotation-only configs built that way. Make `preview` a thin generator of that config, and make `--against` a **pure post-hoc differ over two existing `annotation_results.json` files** — no new runs, works on every run already on disk. Prerequisite: add a `confidence` field to the dynamic annotation decision model (`AnnotationDecision.confidence` is declared and never populated; the dynamic `_DecisionBase` has no such field and sets `extra='forbid'`, so the model literally cannot return it; every decision in `social/v3-annotation-only` reads `null`). Without it, "sample low-confidence first" is unimplementable at the stage where every documented spec failure lives.

## 5. Theme C — Establish the noise floor

**C1. Replicates, confidence-stratified.** This is §8a item 2, marked **[need]** and "Cheap: one extra run per project." The measurement is better than anyone proposed. Diffing dementia v2 vs v3 abstract decisions over the 1,905 common studies: 98 flips (5.1%), stratified by v3's self-reported confidence — `≥0.95`: 3/713 = **0.4%**; `0.85–0.95`: 39/796 = **4.9%**; `<0.85`: 56/396 = **14.1%**. A 34× spread. Two consequences: self-reported confidence is genuinely predictive of instability in this corpus (a result the paper does not have), and **21% of items carry 57% of the flips**, so a usable unstable-decision queue can be built *today at zero token cost from confidence alone*.

Order: (i) build the review queue from the low-confidence tail — free, lands this week; (ii) replicate-sample **stratified by confidence**, not uniformly (uniform k=3 over 15% spends most of its budget in the ≥0.95 stratum where the flip rate is 0.4%); (iii) add `confidence` to the annotation model (per B9) and default `confidence_reporting` to True, or the calibration report ships empty for most users; (iv) record actual sampling params (temperature/seed/n, or "provider default, unspecified") in the artifact — nothing in the package passes any of them today; (v) run one byte-identical-prefix replicate per project, because the v2/v3 pair differs by a gateway routing prefix and the paper's headline 8.6% currently conflates resampling noise with provider routing. Frame the output as a *floor on detectable effect size*, never as a quality score.

**C2. `autonima diff <run_a> <run_b>` — expose the stage hashes.** Every run writes seven per-stage semantic hashes to `execution_manifest.json` and they are never queryable. I ran the comparison by hand and it reproduces the paper's hand-derived claims instantly, and finds one live error (see §7). Two corrections to the proposal:

- `stage_signature_payloads` is **not** persisted — only `stage_hashes` is. Add the payloads to the manifest dict (one line, already computed) so historical runs are diffable at clause level without reparsing configs that may no longer validate.
- **Fix the noise partition or drop the noise-floor claim.** "Stage signature identical → nondeterminism" is false whenever an *upstream* stage differs. `v3-all_pmids` vs `v3-search-all_pmids` have identical annotation signatures but different search signatures, so they annotate different pools; every annotation flip between them would be labelled nondeterminism and folded into a published noise floor. Classify as nondeterminism only when all upstream stages match **and** the item's own input hash matches — `study_input_hash` inside every annotation `cache_signature`, `_coordinate_cache_signature` per study, `_screening_cache_signature` for screening. Everything else goes to a third bucket, "upstream inputs differ — not attributable."
- Print the field list the payloads actually cover, and explicitly flag `criteria_mapping` and the other `_strip_noise` exclusions as **not compared**, so "signatures identical" is auditable rather than trusted.
- Add `--assert-differs-only-in <stage>` and run it in CI over all runs in the results repo.

**C3. Cross-model second rater.** §8a item 1, currently **[partial]**. Not in the product: every stage takes one model string. The mechanism works — on the existing `social/v3-all_pmids-multi_analysis-ft` vs `-gpt52` pair, 6,428 common decisions, 736 disagreements (11.45%), and **100% of disagreements carry at least one criterion id**, so clause localisation needs no human labels.

But **normalise by base rate or the report is useless.** Raw symmetric-difference counts rank `GLOBAL_I2` 619, `GLOBAL_I1` 543 — that is just a ranking of the most-cited clauses and will name I1/I2 in every project forever. Divided by base rate it inverts into exactly the expected shape: `AFFILIATION_ATTACHMENT_I1` 0.611, `SOCIAL_COMMUNICATION_I1` 0.573, `PERCEPTION_SELF_I1` 0.567 … down to `GLOBAL_E1` (rest/fixation baseline) 0.213 and `GLOBAL_E2` (between-group) 0.104. Construct-definition criteria ambiguous, mechanical criteria crisp. Suppress clauses below ~30 base citations. State the asymmetry as a hard rule in the JSON: **disagreement is evidence of specification ambiguity; agreement is not evidence of correctness**, because the models share training data. Make the human arm explicit and small — emit a fixed 25-item stratified adjudication worksheet and refuse to state the spec-vs-expertise diagnosis until it is filled in. `AUTONIMA_MODEL_PREFIX` is applied globally in `resolve_model_name`, so a cross-provider rater needs that made per-call.

## 6. Theme D — See the search ceiling before paying for it

**D1. Parse the whole PubMed record. This is the most consequential small fix in the document.**

`pubmed.py:370` does `article.find('.//Abstract/AbstractText')` — one element, `.text`, which stops at the first child node. A four-section structured abstract yields only its first section. Verified against live PubMed: PMID 12727696 has 1,303 chars across four labelled sections; `executive_function/v1/outputs/search_results.json` stores 264. Corpus-wide, abstracts under 450 chars: executive_function/v1 **26.6%**, dementia/v1 **30.6%**, cue_reactivity/v6 **28.3%**, vbm_of_substance_use/v2-recent **30.4%**. `ArticleTitle` truncates at the first inline `<i>`. `.//MeshHeading/DescriptorName` and `.//PublicationType` are never collected at all — the richest controlled-vocabulary signal in the record, discarded.

Roughly twenty lines: `findall` + `''.join(elem.itertext())`, joining as `f"{label}: {text}"` when `@Label` is present; MeSH and PublicationType into `Study.metadata`, which already exists as a free slot. Three requirements:

- **Do not bump the global `CACHE_SCHEMA_VERSION`.** That makes `manifest_is_modern` false, which raises `UnsupportedCacheError` under the default policy, which forces `--cache-policy ignore`, which deletes every stage artifact of every run — a full re-run of nine projects. Instead put an abstract-parser version into the **search** stage hash only, and make `_load_cached_search_results` actually inspect `data['cache_signature']`, which it currently reads past and ignores. That turns a nine-project full re-run into a re-fetch of ~50 batched efetch calls per project plus a screening re-run.
- Record `abstract_section_count` and `abstract_char_count` in `Study.metadata` at parse time — without them the paired re-analysis cannot separate "was truncated" from "genuinely has a short abstract," and that separation is what the paper reinterpretation rests on.
- Put MeSH in metadata (free) and make **prompt exposure a separate experiment**, so the abstract-repair effect is measured with one variable moving.

**D2. `autonima search-check`, inverted: leave-one-clause-out first.** The seed-based version certifies the query in exactly the case that motivated it. cue_reactivity's v5 query already contained `food cue*`, `sexual cue*`, `erotic cue*`, `Feeding Behavior[mh]` and `erotica[tiab]` and still reached **24% of the natural-reward gold**; an author thinking in cue/craving terms would have supplied cue/craving seeds, the tool would have returned 10/10 hits, and it would have issued a clean bill of health on the worst search in the corpus. A false all-clear is worse than no signal, because it ends the investigation.

So make the primary output **leave-one-clause-out**: for each top-level conjunct, report the esearch `Count` with that clause dropped, and sample ~10 titles from the records it removes. n+1 requests, zero seeds, no prior knowledge — and it would have shown the cue_reactivity author that their cue/craving conjunct was deleting food-picture and incentive-delay papers. Keep seeds as a strictly secondary confirmation printed as "seeds reached: k/n" with a standing caption that a full score means nothing about coverage. Reuse `run_baseline_searches.py:221 gold_found()` (already builds `(pmid[uid] OR ...) AND (query)`) rather than reimplementing. Fix `app.jsx:1779`, which ORs `${pmid}[PMID]` clauses into the query text — that guarantees those papers are returned and hides precisely the failure this command exists to find.

**D3. Tracer studies, framed as a one-sided test.** `search.tracer_pmids`, tagged and tracked through every stage, reported after the search stage alone so `run-search` becomes a minutes-long query loop. The plumbing is closer than it looks: `pubmed.py:75` already unions `_load_pmids()` with query results and `run-search` already exists with a stage-aware summary, so the delta is a provenance flag plus a report. **Report "tracers your query missed" as a named list, never "tracer recall" as a number.** Self-selected seeds are memorable canonical papers — the ones any query finds — so tracer recall is an *optimistically biased upper bound*, not a lower bound as originally framed. Report the non-tracer delta (records gained/lost) on every query edit so the seed set cannot be silently overfit. Dedup before building Study objects. Keep `tracer_pmids` out of `stage_signature_payloads['search']` so the diagnostic is free to re-run.

**D4. Citation chasing (unreviewed; hold for Tier 3).** The only proposal that lifts recall above the ceiling of *any* single query, and the specific practice the source meta-analyses used that autonima lacks. Europe PMC's `/MED/{pmid}/references` and `/citations` return PMIDs natively, so this needs no identifier-resolution layer and can be prototyped inside `PubMedSearch` with no registry. Its yield is directly measurable on the benchmark — run it on decision_making (0.601) and problem_solving (0.611) and report what fraction of the missing ~40% it recovers. Gate it on F1 (token accounting) first: each round adds abstract screening on corpora already at 4,881 studies. A negative result here is publishable and should be reported honestly.

## 7. Theme E — Make the extraction funnel visible and actionable

**E1. Enrich `missing_fulltexts.csv`.** Add `pmcid`, `reason` (`no_pmcid | pmcid_no_text | unmatched_in_source:<name> | incomplete_html`), `title`, `journal`, `year`, `doi`. Derive `reason` from `study.pmcid` (already serialised to `fulltext_retrieval_results.json`) joined against pubget's `text.csv` membership — **not** from the dead `not_found` list at `pipeline.py:693`, which makes this cheaper than proposed. Under an hour, and it immediately splits dementia v3's 994 undifferentiated rows into **762 publisher-route and 239 PMC-retry**.

**E2. Mechanical completeness detection.** The only incompleteness detector in the package is a prompt clause consumed at `screener.py:382`, and a paper flagged incomplete is dropped from parsing entirely (`pipeline.py:888` selects only `INCLUDED_FULLTEXT`) even if its tables retrieved fine. The mechanical signal is trivially strong: of executive_function v1's 80 incomplete rows, **79 are Elsevier `text.txt` files with median size 1,718 bytes** (min 864, max 2,470) against a 17,775-byte corpus median, visibly terminating after `## Abstract`. A length-plus-section-header rule separates these at ~10× margin.

Resolve the design's internal contradiction — feeding the flag into the prompt while the model still decides adds an anchor and removes nothing. Take the clean version: the mechanical assessment alone sets `FULLTEXT_INCOMPLETE`, the study is never sent for full-text screening, and clause 8 is **deleted** from `screening/prompts.py`. That leaves the prompt byte-identical for every study that *is* screened, so only stub studies lose their cache rather than every full-text decision in every run. Do not oversell it: the cost saving is ~80 calls, it recovers no coordinates (stubs have no tables), and "incomplete" is a PRISMA counter, not one of the flip-rate-bearing agreement metrics. The real payoff is that incompleteness becomes a property of the artifact rather than a verdict fused into eligibility. Ship length/section/table-count first; `CHALLENGE_PATTERNS` only matter once a manual-ingest path exists.

**E3. Gate ledger — relocated.** Write it where the **gate** runs (`load_activation_table_map` / `_map_pmids_to_text`), one row per candidate table in the *source* with `gate_decision ∈ {coordinates_match, ace_candidate, gate_rejected}`, plus one row per in-scope study with zero source tables. A ledger written from `_execute_coordinate_parsing` sees only post-gate survivors: in dementia v3, **95 of 157 full-text-included studies have no activation table at all** (58 ACE'd HTML, 19 Elsevier, 18 pubget — 17 of those 18 having tables in `tables.csv` that the gate rejected), and among the 35 pubget final studies, 61 of 98 source tables were dropped. It would document the 39% that works and omit the 61% that does not. Keep the three correctness fixes verbatim: `source`/`gate` fields on `ActivationTable`; `process_single_table` returning a typed result so `load_failed` and `api_error` stop reading as success; `processed_count` counting non-empty yields (today `tables_processed` is a call count). Keep zero-yield caching — `pipeline.py:1221` filters on `s.analyses`, so every rerun re-pays for the same empty LLM calls; it is a one-word change.

**E4. Funnel report (unreviewed).** `outputs/funnel.csv` + figure: search → abstract included → full text obtained → complete → full-text included → ≥1 table → ≥1 coordinate → exported. Driven by E3 so each drop is attributable. Two headline ratios in the CLI summary. This is one of the few honest self-diagnostics available without a gold standard, it sits on the dominant bottleneck, and the figure is directly reusable as a paper supplement instead of being hand-assembled per project (dementia's was, at `REPORT.md:214-226`). Ship after E3, not before. Label the influence ranking as prioritisation, never as a quality claim.

**E5. `autonima acquire` (Tier 3).** The scripts already work (`open_pubmed_in_browser.py` with elink prlinks + PMC idconv + ezproxy prefix + a save-as-`<PMID>.html` bookmarklet; `move_downloaded_pmid_html.py`; `ace_get_unavailable.py` with `CHALLENGE_PATTERNS`). Promoting them lowers cost and makes the step reviewable; it does not raise the recovery rate, so it is not urgent. Two design corrections when it happens: `manual_dir` must be **project-scoped, explicitly declared**, not a run-managed `<run>/retrieval/manual_html/` (these projects share one corpus at `articles/` across v1/v2/v3, so a run-scoped dir rebuilds the per-version archaeology it is meant to kill); and `--ingest` must **copy, not move** — moving makes an irreversible edit to `~/Downloads` on a heuristic filename match. Keep it browser-assisted and user-driven; `CHALLENGE_PATTERNS` existing at all is evidence that headless fetching invites an arms race.

**E6. Decision ledger + three-valued NiMADS status.** `nimads_models.py:394` carries the comment *"Default to False if no decision was made for this analysis-annotation pair."* In dementia v3, **146 of 478 exported analyses (31%) receive `False` in four columns purely because no decision exists**, indistinguishable in the NiMADS file from an evaluated rejection — and `meta.py:_analysis_ids_for_column` selects on exactly that boolean, so "not evaluated" is being fed to NiMARE as "excluded." That is a correctness bug in the primary deliverable.

Ship in this order: (i) the **coverage assertion** as a warning at the annotation stage — "N of M parsed analyses received no decision for column X" prints 146 of 478 immediately, and that number is worth more than any CSV; (ii) add a parallel `<column>__status` note key with the enum (`included | rejected | not_evaluated | no_valid_coordinates | not_parsed | parse_failed | study_excluded_at:<stage>`) so the NiMADS file itself is honest while the boolean stays for NiMARE compatibility; (iii) `outputs/decisions.csv` joining the per-stage records, additive and schema-versioned, with the study-level funnel as a *superset* of `missing_fulltexts.csv` using the same column names so existing scripts keep working. Drop the "negatives lost permanently" framing — they are on disk in every run (`annotation_results.json` in dementia v3 holds 2,879 decisions of which 1,137 are negative); this joins and disambiguates, it does not rescue.

**E7. Benchmark-mapping validation — keep it in `scripts/`.** `resolve_analysis_dir` returns `None` for both NOT_FOUND and AMBIGUOUS, and callers print `SKIP:` and continue; the script exits 0 as long as *any* row was produced, so losing one sub-analysis writes the CSV and reports success. Make it a typed result, exit non-zero on unresolved keys unless `--allow-unmapped`, and add the **orphan check** (a benchmark directory with no mapping entry) — the genuinely new one, and the failure mode where a sub-analysis silently leaves a table. Do **not** move this into the package and do not invent an `evaluation:` config block: a practitioner has no manual analyses to map, and the block does not exist. Drop the PMID-normalisation check (`benchmark_pmids.normalize_pmid` already centralises it and the mapping files carry no PMIDs). Make `source` **optional and emitted into the comparison output**, not required in the schema: a row reading `logical_reasoning <- demand_mni_final (source: unrecorded)` puts the gap in front of a reader every time the comparison runs, which is more pressure than a validator error silenced with a flag on day one. A required free-text field would not have stopped anyone writing `source: "demand"`.

## 8. Theme F — Make an expensive run cheap to own

**F1. Meter every LLM call.** All five `chat.completions.create` sites discard `response.usage`; `grep -rn "usage|prompt_tokens|total_tokens|tiktoken"` over the package returns one unrelated NCBI comment. **This is the only thing blocking §S1**, which PAPER_OUTLINE.md:679 already calls "one cheap item with disproportionate effect."

Architecture correction that matters: `AnnotationClient` does **not** inherit from `GenericLLMClient` — `client.py:135` composes it and reaches through to `self._client.client.chat.completions.create`. A base-class mixin would miss the two most expensive call sites. Add one `create_completion(**kwargs)` method to `GenericLLMClient` that performs the call, records usage and returns the response, and route all five sites through it. Record **one line per HTTP attempt**, not per logical item, so the 3 retries at `client.py:196` and the SDK's own `max_retries=2` are both visible; record status so this file doubles as A4's failure ledger. Fix `_read_stage_counters`, which emits only `{decisions, annotations}` for annotation with no processed/reused, so cost cannot currently be split billed-vs-cached in the most expensive stage. Half of §S1 is already derivable — `execution_progress.json` has per-stage `started_at`/`completed_at` — so only the cost column is genuinely blocked.

For the estimate, **do not use median tokens/item**: that works for abstract screening and is close to useless for full-text screening and annotation, where the prompt embeds the retrieved document and length is dominated by document size — precisely the expensive stages. The pipeline already has the text in hand; sum `len(prompt)/4` over the real pending prompts. That is a measurement, not a guess, and it costs nothing. **Drop `--max-cost` until F2 lands** — aborting annotation mid-stage today discards every call made, because results save once at the end; a budget cap that guarantees you pay and keep nothing is a footgun. Date the price table and put the effective date in `cost_report.json`.

**F2. Checkpointing — different treatment per stage.**

- **Annotation:** do *not* call `_save_results_by_study` per study. It does a full read → pydantic-construct-every-row → full rewrite; `executive_function/v1-2010`'s artifact is 19.6 MB / 27,228 decisions / 1,130 studies, so per-study calls mean ~22 GB of read+write and ~30M constructions serialised behind a global spin-lock while 25 workers block — on a stage that currently takes ~13 minutes. Append signed decisions to `annotation_results.partial.jsonl` (O(1), no read-modify-write, no whole-file lock), compact at stage end and on stage start if a partial exists. Flush per completed study, which is the unit `_get_annotations_with_complete_results_for_study` already validates by count and signature, so a torn tail row is caught and reprocessed.
- **Parsing:** do *not* checkpoint per table. The cache is keyed per **study** but the parallel work unit is a **table**, flattened across studies. Persisting per finished table means a study carrying 2 of its 5 tables gets written under a signature that validates, and on resume it is skipped and its remaining coordinates are silently lost. Coordinate extraction is the documented binding constraint; a change that silently under-extracts is worse than losing an hour. Group jobs by study and persist only when a study's last table completes — or add `tables_parsed` to `_coordinate_cache_signature`, a two-line change that makes the per-table version safe.
- **Prerequisite:** give `_acquire_lock` a timeout and stale-lock detection. It is currently an unbounded spin with no recovery, so a process killed between `os.open` and `_release_lock` deadlocks every future run forever. Building crash-safety on a lock that deadlocks on crash is self-defeating.

**F3. `autonima plan`.** `preview_execution_changes` and `build_cache_plan` already exist and are tested; they are wired only to the webui. `--dry-run` prints two static lines. Expose the plan as a stage table plus F1's cost projection. **Drop `autonima status`** — exactly one of 95 progress files is stuck at `running`, and it already carries `updated_at`; fold it into `plan` as a two-line header reporting "no progress since `<updated_at>`" rather than asserting the run is dead.

**F4. Meta stage: lead with the manifest, not the memory fix.**
- Move `column_output_dir.mkdir` to **after** the skip checks, so a skipped column never creates a directory. Write `meta_manifest.json` + per-column `status.json` recording which of the five distinct early-return paths fired, plus `n_studies`, `n_analyses`, `skipped_without_valid_coords` (already computed, only printed), estimator args and wall clock. Four empty directories exist today — and three of them are the **same column (`increased_gm`) across all three vbm_of_ptsd runs**, a systematic signal about that column that is currently unreadable from the artifacts.
- Wire `--columns` and `--skip-existing`; both parameters already exist and the CLI simply never passes them. **Do not add `--continue-on-error`** — `fail_fast` already defaults False and the except block already continues; adding a flag for existing behaviour invites the wrong mental model.
- Key `--skip-existing` on manifest status, never on directory emptiness: the four existing empty dirs would be retried forever, and a partially-written column skipped forever.
- Make `--isolate-columns` the headline, not an aside — it is the only part that survives an OOM. And **measure before building**: run `/usr/bin/time -v` on an executive_function column at `n_cores=9` vs `n_cores=1`. The retained `results[column]` deep-copies are real (`MetaResult.__init__` deep-copies the fitted estimator, which holds the Dataset) but are tens of MB per column; the archived batch script passes `n_cores: 9`, and montecarlo/kernel transforms at nine-way parallelism are the far more likely OOM. Dropping the accumulation is free and correct — `cli.py:671` uses only `len(results)` — but it is probably not the fix.

## 9. Roadmap

Weighted by (documented-failure severity) × (breadth of users affected) / effort.

### The single highest-value thing

**B1 — `inclusion_criteria_not_met` with a required evidence span, plus the screening-side citation validator.**

It is the substrate for the dominant failure mode. Today, 94% of executive_function's exclusions and 99.7% of social's carry no machine-readable reason at all, so "this criterion never fires" and "this criterion only ever fails" are the same observation. Every other item in Theme B — the sole-cause index, criterion-scoped review, PRISMA reasons, the recheck strata — is computed over a biased 6% of the screening evidence until this lands. It needs no benchmark, no new UI, no second rater, and no better model. It is the one change that converts the paper's central finding ("the spec was wrong, and only reading the rationales separates that from model incompetence") from a limitation into a product feature. And the prose fallback has already been tried and measured at 0–33% — asking harder is not an option.

Preflight (A1) is cheaper and should ship first mechanically, in the same week. It is not the highest-value thing because it catches configuration *accidents*; B1 catches specification *errors*, which are more common, more expensive, and the thing the product exists to help with.

## 10. Explicitly rejected, and why

**Capture-recapture coverage estimation.** Tested on this repository's own data. Taking cue_reactivity v5's actual query as sample A (1,170 hits) and a differently-worded cue/craving variant as B (737, overlap 694), Chapman gives N̂ = 1,242 against a union of 1,213 — **97.6% estimated coverage**. True recall of that union against the 191-paper gold is **74.9%**, and the natural-reward column that motivated v6 sits far below. It would have printed "your search is essentially complete" at the exact moment the search was reaching 24% of natural-reward gold, because two queries sharing a blind spot cannot see it. Shipping it labelled "estimate, assumptions printed" does not help; a 97.6% will be believed. The proposed calibration study also cannot be run — `baselines.yaml` variants share a byte-identical modality clause (`run_baseline_searches.py` already computes a "modality ceiling" because it knows this), and decision_making v2 and v3 carry character-identical query strings. Salvage only the observables: per-query hit count, per-query unique contribution, union curve.

**Mechanical coordinate fallback.** Measured: joining `pubget_data/coordinates.csv` against `final_results.json` at (pmcid, table_id), dementia v3 has 36 mechanical tables belonging to final studies and **0** with zero LLM points; social/v3-all_pmids 0 of 27; cue_reactivity/v6 0 of 122; executive_function/v1 0 of 7. Across all 90 run dirs, studies that had activation tables and ended with zero analyses: 0 in every main project version. "The single largest recoverable coordinate mass in the system" is worth zero points, and one-analysis-per-table units would cost real analysis-level precision.

**Per-decision agree/disagree adjudication UI.** Wrong unit, and the sampler is anti-correlated with the failure it is sold on. Self-adjudication measures spec-*application* fidelity; the documented failures are spec-*correctness* failures where the author would correctly mark AGREE. Low-confidence/unstable/boundary sampling routes systematically away from the 30 executive_function FNs, which were high-confidence and stable. It also cannot sample that way at annotation, where `confidence` is `null` on every decision. Replaced by B3.

**Polarity lint as originally specified.** Run over ~900 real inclusion criteria it fires at 5.8% and the hits are overwhelmingly *permissive* phrasings. It flags `executive_function/v2-annotation-only.yaml` inclusion criteria [4] and [5] — "A main effect of task against implicit baseline qualifies. Do not require an overt response." Those two lines are the successful repair of the flagship documented failure. Narrowed and demoted to INFO in B8.

**DEAD-criterion and ALWAYS-SATISFIED flags as verdicts.** 8 flags, 0 true positives across four configs. In the corrected executive_function config, two of the three never-fired criteria are the repair itself. Permissive and guidance clauses are structurally uncitable and will always look dead.

**Sole-cause as a risk flag or a diagnostic ranking.** A correctly-specified restrictive criterion produces a high sole-cause count *by construction*. On social the ranking puts the 10-errors/0-correct criterion **last of nine**. Keep the index, drop the ranking.

**Repo-wide metrics-schema redesign and metric rename.** The premise is false: every `performance_metrics.json` already pairs a `counts` block carrying the denominators (`meta_total`, `meta_in_search`, `included_total`, full-text availability) with Wilson CIs per metric. And the "live substitution" never fires — the precision fallback copies the same float, and all 52 artifacts contain `recall_all_meta`. Do the 20-line version instead: delete both fallback chains and raise a `KeyError`; add `schema_version`/`execution_id`/`config_hash` (all already in the manifest); add a `denominator_key` string per metric.

**`${config_dir}` path templating sold as portability, and hashing the unresolved template.** 56 of 60 `root_path` values resolve on this machine; the corpus is unified on one absolute prefix. What a second person lacks is the multi-gigabyte, non-distributable `articles/` tree — rewriting the roots produces a config that resolves to a path containing nothing, which is the silent-empty-source failure dressed as portability. And hashing the template would make one config on two machines produce the same retrieval stage hash over different bytes: a new class of false-valid cache, in a proposal whose stated lens is eliminating silent failure, bought with a `CACHE_SCHEMA_VERSION` bump that forces recompute on all existing runs. Keep only the `~`/`$ENV` expansion hygiene (~30 lines, no cache impact); the honest portability fix is a **content fingerprint** of each resolved source in the manifest.

**Pluggable search-backend registry.** ~50 lines that buy nothing until an adapter exists, and the adapter is where identifier resolution, filter translation (`Humans[mh] AND English[lang] NOT (review[pt] ...)` lives inside a raw query string with no cross-source equivalent) and a preprint-driven precision collapse all land. Its stated justification was to be the substrate for capture-recapture (rejected) and citation chasing (reachable today via `_make_request_with_retry`). Ship only the real bug: `config.py:238` validates `database in ['pubmed','pmc']` while `pipeline.py:290` raises on anything but `pubmed`.

**Leave-k-out resampling stability and unthresholded R² between refit maps.** NiMARE's `Jackknife._transform` already deep-copies the estimator, refits leave-one-out for every experiment and reports per-cluster proportional contribution — and is selectable as the string `'jackknife'`, which `meta.py:275` simply never passes. Refitting B times multiplies a workload that has already OOM'd. And R² between maps refit from heavily overlapping data is ≈1 by construction, so it will look reassuring and say nothing. Keep layer (a) only, renamed *cluster contribution summary*: on `social/affiliation_merged` the existing FocusCounter TSV already shows **8 of 13 significant clusters with zero contributing analyses** and one cluster driven by a single analysis — a striking, unreported robustness finding reachable in five lines of pandas over a file that already exists. Report per-cluster survival with the resample design stated, so it cannot be read as a p-value.

**`--max-cost` (for now).** Aborting annotation mid-stage discards everything, because results save once at the end. Revisit after F2.

## 11. What this changes about the paper

Seven items touch PAPER_OUTLINE.md directly. Three unblock a `[need]`; two change a claim; two are corrections that should land before a reviewer finds them.

**1. D1 (abstract truncation) changes §1 and §8a, and it is the item to take most seriously.** 26–30% of abstracts in four separate projects are single-section fragments; METHODS and RESULTS — which the screening criteria ask about — are gone before the screener reads a word. Among the 127 executive_function gold papers in search, **9 of the 10 with a truncated abstract were excluded at abstract screening, versus 7 of 117 with a full abstract**; "not specified/reported in abstract" rationales run 46.1% vs 31.3% (ef), 33.0% vs 19.9% (dementia), 31.3% vs 17.0% (cue_reactivity). §8a currently attributes executive_function's abstract-stage false negatives to over-strict user criteria — the paper's flagship "the spec was wrong" case. **Specification error and information starvation are confounded in the current results.** State it as a hypothesis until the paired re-run exists (n=10 is small and truncation correlates with era and journal), record `abstract_section_count` so the re-analysis can separate "was truncated" from "is genuinely short," and re-run all arms on one corpus vintage per the outline's own rule.

**2. F1 unblocks §S1 outright.** The outline says "cost needs per-stage token accounting, which may require adding it to the pipeline if it is not already logged. Worth checking before promising the cost column." Checked: there is zero token accounting anywhere in the package. Half of §S1 is already derivable from `execution_progress.json`'s per-stage `started_at`/`completed_at`; only cost is blocked, and the sequencing note calls §S1 "one cheap item with disproportionate effect."

**3. C1 unblocks §8a item 2** ("Test–retest self-consistency… Cheap: one extra run per project. **[need]**"), and improves on it: confidence-stratified replicates give the same information for roughly a third of the tokens, and the confidence-vs-instability calibration (0.4% / 4.9% / 14.1% across three strata) is a result the paper does not currently have. It also lets §8b separate genuine resampling noise from gateway routing, which the headline 8.6% currently conflates.

**4. C3 promotes §8a item 1 from [partial] to a method.** The existing `-ft` vs `-gpt52` pair already yields 736 disagreements with 100% criterion-id coverage; base-rate normalisation turns that into a clean construct-vs-mechanical separation (0.45–0.61 vs 0.10–0.21).

**5. C2 kills a live error in the paper plan.** PAPER_OUTLINE.md:651-652 plans to use "the `multi_analysis` variants" for a prompt-type comparison. I checked all 15 social runs: **every one is `prompt_type: multi_analysis`**, and `v3-all_pmids` vs `v3-all_pmids-multi_analysis` have **all seven stage hashes identical** with configs differing by exactly one line (the output directory). **6. A5 corrects a PRISMA number.** `social/v3-search-all_pmids` reports `total_identified: 1510` / `final_included: 841` against **536 distinct papers** — a 57% overstatement, with 445 duplicate pairs screened twice.
